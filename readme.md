# Energy-Efficient Task Allocation in Digital Twin Enabled UAV Networks Using Jaya Algorithm

## 1. Introduction

Modern Unmanned Aerial Vehicles (UAVs) generate large amounts of data that must be processed efficiently to support tasks such as surveillance, delivery, and disaster response. However, the limited onboard computing capabilities and battery capacity of UAVs make local processing insufficient and energy-intensive. As a result, a multi-layer UAV network architecture has emerged, where tasks are distributed across UAVs, Ground Base Stations (GBS), Mobile Edge Computing (MEC) servers, and cloud servers.

To enable efficient task distribution, Digital Twin (DT) framework is integrated into the UAV network. The DT maintains real-time virtual representations of physical UAV network components, allowing the system to monitor network and resources accurately. This real-time information supports predictive optimization and decision making, thereby improving task allocation efficiency.

---

## 2. Problem Formulation

Consider a Digital Twin enabled UAV network system, where UAVs generate computational tasks. These tasks are to be executed at the UAV, Ground Base Station (GBS), Mobile Edge Computing (MEC) server, or the cloud while minimizing energy consumption and ensuring efficient resource utilization.

### Notation
- T = {1, 2, ..., n} : Set of tasks generated by UAVs
- G = {1, 2, ..., g} : Set of Ground Base Stations (GBS)
- x_i ∈ {0, 1, 2, 3} : Decision variable representing execution location for task i

### Execution Locations
- x_i = 0 : Task is executed locally at the UAV
- x_i = 1 : Task is executed at the associated GBS
- x_i = 2 : Task is forwarded to a neighboring GBS/MEC
- x_i = 3 : Task is executed at the cloud

The task allocation problem aims to determine suitable values of x_i for all tasks such that energy consumption is minimized while maintaining balanced utilization of GBS resources.

---

## 3. Energy Consumption Model

Energy consumption represents the total energy expended by a UAV to complete a task, including computation energy, transmission energy, and hovering energy while waiting for offloaded results. Tasks executed locally consume only computation energy, while offloaded tasks require transmission energy and hovering energy during the waiting period.

### Local Execution at UAV (x_i = 0)

When a task is executed locally, only computation energy is consumed:

E_i^local = κ × C_i × f_uav²

Where:
- κ : Effective capacitance coefficient
- C_i : CPU cycles required for task i
- f_uav : UAV's CPU frequency

### GBS Execution (x_i = 1)

When a task is offloaded to the associated GBS, the UAV consumes transmission energy and hovering energy while waiting for the result:

E_i^gbs = E_i^tx + E_i^hover

The transmission energy is:

E_i^tx = (P_tx × D_i) / R_i

The hovering energy accounts for the time spent transmitting data, processing at GBS, and receiving results:

E_i^hover = P_hover × (D_i/R_i + C_i/f_gbs + D_i^out/R_i)

Where:
- P_tx : Transmission power
- D_i : Input data size of task i
- R_i : Transmission rate (air-to-ground)
- P_hover : Hovering power consumption
- f_gbs : GBS CPU frequency
- D_i^out : Output data size

### Neighboring GBS/MEC Execution (x_i = 2)

When a task is forwarded to a neighboring GBS or MEC server, additional forwarding delay is incurred:

E_i^mec = E_i^tx + P_hover × (D_i/R_i + t_forward + C_i/f_mec + D_i^out/R_i)

Where:
- t_forward : Forwarding delay between GBS nodes
- f_mec : MEC CPU frequency

### Cloud Execution (x_i = 3)

When a task is offloaded to the cloud, backhaul transmission delay is added:

E_i^cloud = E_i^tx + P_hover × (D_i/R_i + t_backhaul + C_i/f_cloud + D_i^out/R_i)

Where:
- t_backhaul : Backhaul transmission delay to cloud
- f_cloud : Cloud CPU frequency

### Total Energy Objective

The total energy consumption is defined as the sum of energy consumed by all tasks:

f₁ = Σ E_i  (for all i ∈ T)

Minimizing f₁ ensures extended UAV operational time.

## 4. Load Imbalance Model

GBS nodes serve multiple UAVs simultaneously and possess limited computing resources. If tasks are unevenly distributed, some GBS may become overloaded, leading to increased processing delays and reduced system reliability. Therefore, balancing the load among GBS is an important objective.

### Tasks per GBS
Let n_j denote the number of tasks assigned to GBS j, where j ∈ {1, 2, ..., g} and g is the total number of GBS.

### Average Load
The average GBS load is given by:

μ = (1/g) × Σ n_j  (for all j ∈ G)

### Load Imbalance (Standard Deviation)
The load imbalance is defined as:

f₂ = √[(1/g) × Σ (n_j - μ)²]

A smaller value of f₂ indicates more balanced resource utilization across GBS.

---

## 5. Fitness Function

The task allocation problem involves conflicting objectives. Executing tasks locally at UAVs may reduce hovering energy but increases computation energy due to limited processing capability. Offloading tasks to GBS reduces computation burden but incurs transmission and hovering energy costs. To capture this trade-off, a weighted sum approach is used to define a single fitness function.

### Normalization
Since energy consumption and load imbalance have different scales, normalization is applied:

f̂₁ = (f₁ - f₁_min) / (f₁_max - f₁_min)

f̂₂ = (f₂ - f₂_min) / (f₂_max - f₂_min)

### Weighted Fitness Function
The overall objective is to minimize the following fitness function:

Minimize F = w₁ × f̂₁ + (1 - w₁) × f̂₂

Where w₁ ∈ [0,1] is a weighting parameter. By adjusting w₁, the system can prioritize either energy efficiency or balanced resource utilization.

Recommended: w₁ = 0.6 (prioritize energy slightly)

## 6. System Design

The considered UAV network system consists of a multi-layer physical computing architecture designed to support task processing in aerial environments.

### Physical System
The system includes UAVs, Ground Base Stations (GBS), Mobile Edge Computing (MEC) servers, and the cloud. UAVs are connected to nearby GBS through air-to-ground wireless communication, where each UAV is associated with a single GBS. The GBS nodes are further connected to MEC servers, which in turn are connected to the cloud server.

### Computing and Storage Capabilities
Each layer in the system has different computing and storage capabilities:
- **UAVs**: Limited onboard computing and storage resources, allowing only basic local processing and caching
- **GBS**: Moderate processing and caching capacity, serving multiple UAVs within their coverage area
- **MEC Server**: Higher processing capability and larger cache capacity compared to GBS
- **Cloud**: Virtually unlimited computational and storage resources

### Caching Strategy
- UAVs store only static and non-changing information, such as map data
- GBS nodes maintain cache contents related to their respective coverage areas, including local environmental data
- The MEC server contains cache information from all GBS within its coverage region
- The cloud server is accessed only when the requested information is not available at the UAV, GBS, or MEC

When a task request matches a cached result, the response is delivered directly from that particular cache.

### Digital Twin Model
To support efficient task allocation, the physical UAV network system is mirrored by a Digital Twin (DT). It maintains real-time virtual replicas of UAVs, GBS, network links, and computing resources and continuously updates system information such as:
- UAV locations
- Battery levels
- Available computing capacity
- Cache status
- Communication conditions

By maintaining an accurate and up-to-date representation of the physical system, the DT enables the optimization process to make decisions based on current system conditions rather than static assumptions.

## 7. Jaya Optimization Process

Jaya algorithm uses the system information provided by the digital twin to determine the optimal task allocation strategy. Jaya is a parameter-free population-based metaheuristic optimization algorithm that moves solutions toward the best solution and away from the worst solution in the population. Each task allocation solution, referred to as an individual, represents a complete task allocation scheme where the execution location of every task is specified.

### Algorithm Parameters (Only Two!)
- Population size: N (e.g., 50)
- Maximum iterations: MaxIter (e.g., 200)

### Population Representation
Each individual (solution) is a vector:

X_k = [x_1, x_2, ..., x_n]  where x_i ∈ {0, 1, 2, 3}

### Population Initialization
The process begins by initializing a population of individuals. Each individual is generated by randomly assigning an execution location {0, 1, 2, 3} to every task. This random initialization provides diverse task allocation solutions, which helps the algorithm explore different regions of the solution space.

### Fitness Evaluation
After initialization, the fitness of each individual is calculated using the fitness function. Based on the fitness values, the best solution (lowest fitness) and worst solution (highest fitness) in the current population are identified.

### Jaya Update Equation (Position Update Mechanism)
The key advantage of Jaya algorithm is its parameter-free update mechanism. Each individual updates its position by moving toward the best solution and away from the worst solution. For each individual X_k and each dimension i, the position is updated using:

X_k,i(t+1) = X_k,i(t) + r₁ × (X_best,i - |X_k,i(t)|) - r₂ × (X_worst,i - |X_k,i(t)|)

Where:
- X_best : Best solution in current population
- X_worst : Worst solution in current population
- r₁, r₂ : Random numbers in [0, 1]

The term r₁ × (X_best,i - |X_k,i(t)|) moves the solution toward the best solution, while the term -r₂ × (X_worst,i - |X_k,i(t)|) moves the solution away from the worst solution.

### Discretization
Since the task allocation problem requires discrete execution locations, the continuous values obtained from the update equation must be converted to discrete values:

x_i = round(X_k,i) mod 4

This ensures that x_i ∈ {0, 1, 2, 3} for all tasks.

### Greedy Selection
After updating the position, the fitness of the new solution is evaluated. The new solution replaces the old solution only if it has a better (lower) fitness value:

X_k(t+1) = X_k^new    if F(X_k^new) < F(X_k(t))
X_k(t+1) = X_k(t)     otherwise

This greedy selection ensures that the population quality never degrades.

### Termination
The position update and fitness evaluation steps are repeated over multiple iterations. The algorithm terminates when a predefined maximum number of iterations is reached or when improvements in fitness become insignificant. The final best solution represents the optimal task allocation, which minimizes energy consumption and load imbalance.

### UAV Task Update
After the completion of the Jaya optimization process, the task allocation decision corresponding to the final best solution is selected as the optimal solution. Based on this solution, tasks are executed at their assigned locations in the physical UAV network system, and the results are returned to the requesting UAVs. Subsequently, the Digital Twin is updated to reflect the task execution outcomes and the current system conditions. This updated system information can be used for subsequent optimization cycles, enabling the proposed method to adapt to changes in the UAV network environment.
